# Task 004.2.1 — High-Fidelity Digital Ride Receipt

## Task Summary

Refined only the post-trip digital receipt presented after a completed, rated Ride session.

## Status

Complete.

## Scope

This task does not alter Home, destination search, vehicle selection, or the active ride tracking screens. It replaces the prior sparse receipt composition with a richer, scrollable receipt that consumes the existing completed ride state.

## Visual Source of Truth

`docs/design/fluir-ride-receipt-reference.png`

## Previous Receipt Problems

- Excessive unused white space.
- Weak visual hierarchy around the total and payment state.
- Flat, table-like trip information.
- No prominent route summary or route connector.
- Limited autonomous vehicle context.
- Weak payment/fare presentation and a single basic action.

## Final Receipt Structure

1. Safe-area-aware header with the actual completion date/time.
2. Prominent deterministic total and compact green `Pagado` status.
3. Route card with origin/destination connector and balanced route metrics.
4. Autonomous vehicle asset and assigned vehicle details.
5. Informational payment-method card.
6. Fare breakdown with consistent trip fare and total.
7. Stable local receipt identifier.
8. Download, share, and return-home actions.

## Data Sources

- Destination, route distance, and route duration: existing `RideState` / Mapbox Directions `RideRoute`.
- Origin: existing mocked current pickup display name from `MockHomeMapData`.
- Service label and vehicle asset: existing selected `RideOption`.
- Vehicle ID, payment method, rating, and completed timestamp: existing completed `RideState`.
- Fare: the same deterministic local fare calculation used by the completed ride.

## Receipt Identifier

The prototype identifier is stable while the completed session exists and is derived as `FLR-YYYYMMDD-<vehicle suffix>`, for example `FLR-20260828-001`. It is not regenerated by widget rebuilds.

## Fiscal Disclaimer

This is a digital ride receipt, not a Dominican fiscal invoice or NCF implementation. No RNC, tax certificate, DGII fields, or fiscal claims are shown.

## Vehicle Asset Mapping

The receipt reuses the official prototype PNG selected by the existing ride option ID:

- Standard → `assets/images/vehicles/fluir_standard.png`
- XL → `assets/images/vehicles/fluir_xl.png`
- Comfort → `assets/images/vehicles/fluir_comfort.png`

## Download Behavior

`Descargar recibo` retains the controlled local prototype behavior: it confirms `Recibo guardado para esta sesión.` No file or PDF is claimed or created.

## Share Behavior

`Compartir recibo` opens a local read-only prototype share surface with the completed destination, total, and vehicle. It does not disclose full payment data or invoke a system sharing integration.

## Return Home / Cleanup

The existing return-home callback remains the only exit. It resets the active ride, route, and selected destination through the established Home integration, restoring the normal Home sheet and destination prompt.

## Accessibility

The total, paid status, route endpoints, metrics, vehicle, payment method, identifier, and named actions have text and semantics. Long route labels wrap or ellipsize safely; the receipt scrolls instead of compressing content into a single viewport.

## Responsive / Scroll Behavior

The receipt uses `SafeArea` and a vertical `SingleChildScrollView`, keeping the title/total near the top and all detail/action sections reachable on smaller phone heights. Bottom action spacing preserves room for system navigation areas.

## Completed Timestamp Correction

The existing mock lifecycle previously transitioned into `completed` without storing its timestamp in the terminal scheduling branch. The branch now persists `DateTime.now()` only when it transitions to `RideStatus.completed`; lifecycle order and timing remain unchanged.
